# OpenVPN integration

## Expected installation layout

The panel prefers the **modern layout** produced by the vendored
[angristan/openvpn-install](https://github.com/angristan/openvpn-install)
copy:

```text
/etc/openvpn/server/
├── server.conf              # crl-verify crl.pem · status · management socket
├── client-template.txt      # contains: remote <endpoint> <port>
├── ca.crt
├── server_<rand>.crt/.key
├── crl.pem                  # regenerated by the panel on every revoke
├── ipp.txt                  # IP pool persistence (cleaned on revoke)
├── tls-crypt-v2.key         # server-side key (modern installs)
└── easy-rsa/                # PKI lives here
    └── pki/{index.txt,ca.crt,issued/,private/,crl.pem}
```

The **legacy layout** (`/etc/openvpn/server.conf`, easy-rsa outside the
server dir) is still supported — point `SERVER_CONF`, `EASY_RSA_DIR`,
`INDEX_FILE` and `CLIENT_TEMPLATE` at the right places and re-run
`vpnui doctor`.

Path resolution order is documented in `.env.example` and validated at
startup: a wrong path fails fast with a `vpnui doctor` hint instead of a
half-working panel.

## TLS modes

| Mode | server.conf line | Panel behaviour |
| --- | --- | --- |
| `crypt-v2` (default) | `tls-crypt-v2 tls-crypt-v2.key` | Generates a **unique** client key via `openvpn --genkey tls-crypt-v2-client`, embedded as `<tls-crypt-v2>` in the profile |
| `crypt` | `tls-crypt tls-crypt.key` | Shares the server key, embedded as `<tls-crypt>` |
| `auth` | `tls-auth tls-auth.key 0` | Embeds `<tls-auth>` + `key-direction` |

`tls-crypt-v2` gives every client its own control-channel key: a stolen
profile cannot be reused after its key is revoked, and the server can reject
old keys with `tls-crypt-v2-verify`.

The parser matches directives with word boundaries — `tls-crypt-v2` is never
mis-detected as `tls-crypt`.

## Client profiles

A profile is assembled from:

1. `client-template.txt` (endpoint/protocol/tuning, `remote-cert-tls server`)
2. `<ca>` / `<cert>` / `<key>` extracted from Easy-RSA output (PEM-aware, so
   subjects containing `=` are handled correctly)
3. the TLS wrapping block for the configured mode
4. optional `auth-user-pass` note for password-protected keys (the key
   itself is encrypted — the passphrase is passed to OpenSSL via `env:`, never persisted)

Profiles are stored with mode `0600` under `DATA_DIR/clients/<name>.ovpn`
and served as JSON (`GET /api/clients/:name/config`) or as an attachment
(`?download=1`).

## Revocation and the CRL

`DELETE /api/clients/:name`, inside the PKI lock:

1. `easyrsa revoke <name>` (marks `index.txt`)
2. `easyrsa gen-crl` (fresh CRL)
3. copy the CRL to wherever `crl-verify` points in `server.conf`
   (the panel parses the directive — no hard-coded path)
4. delete the stored profile, remove the entry from `ipp.txt`
5. best-effort `kill <name>` on the management socket (if mounted)
6. audit-log the operation

OpenVPN re-reads the CRL on reload; run `systemctl reload openvpn-server@server`
(or wait for your reload cadence) if you need revocation to take effect
immediately on a freshly restored CRL.

## Auth modes

- **pki** (default): certificates from the shared CA; revocation via CRL.
- **fingerprint**: peer fingerprints in `<peer-fingerprint>` blocks (the
  panel detects this mode and reports it in `/api/status`; provisioning is
  done with the vendored script's `--auth-mode fingerprint`).

## Observability mounts

| Host path | Mount | Enables |
| --- | --- | --- |
| `/var/run/openvpn-server` | rw | management socket → kick sessions on revoke |
| `/var/log/openvpn` | ro | `status.log` → live session list in `/api/status` |

Without them the API still works; `sessions.available` and
`openvpn.managementAvailable` simply report `false` with a reason.

## Host networking prerequisites

- `net.ipv4.ip_forward=1`
- NAT: `iptables -t nat -A POSTROUTING -s <vpn-subnet> -j MASQUERADE`
- the OpenVPN unit enabled (`openvpn-server@server`)

`vpnui doctor` verifies all three with fix hints.

## Multi-device clients

`duplicate-cn` in `server.conf` (the vendored installer's `--multi-client`)
lets one certificate connect from several devices. The panel's listing and
revocation are unaffected — it operates purely on the PKI.
